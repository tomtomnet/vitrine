# vmview

The VM display: QEMU's D-Bus display (`-display dbus,p2p=yes,gl=on`) drawn
into a native Wayland surface. The guest's buffers are attached as they are
when the sizes match (zero copy), or copied into the window's own buffers,
and QEMU is told when each frame reached the screen.

The client files here come from the D-Bus display client of the qemu-gui
research (embed-poc), where the frame path keeps being worked on. Keep them
as they are, so that its changes port over by copying the files:
`sha256sum -c UPSTREAM.sha256` lists the files that no longer match the
version taken. The few changes vitrine needs before the research side has
them are listed under Local changes below, to make again after a copy.
vitrine's own code is `vmview.{h,cpp}`: it attaches to a
running QEMU and puts the display in a widget, or in a window of its own
for full screen (embedded, the display's window takes no input: the
keyboard and the pointer come to the widget, as to any other of the main
window, and VmView hands them to it); `viewsurface.{h,cpp}`: the Wayland
surface the frames go to, vitrine's own, a subsurface of the display's
window that Qt never touches; and `vmclipboard.{h,cpp}`: the host
clipboard shared with the guest through the display's
org.qemu.Display1.Clipboard.

| file | what it does |
|---|---|
| `qmp` | QMP over a connected socket, with fd passing (`getfd`) |
| `dbusdisplay` | org.qemu.Display1: console, input, UI info |
| `listener` | org.qemu.Display1.Listener on its own thread: frames from QEMU |
| `framemailbox.h` | hands frames from the listener to the renderer |
| `renderer` | render thread: zero copy or copy, commit, presentation feedback |
| `swapchain` | the window's own dma-buf buffers |
| `displaywindow` | the QWindow: input, grab, cursor, guest size |
| `waylandextras` | shortcut inhibition, pointer lock, relative motion |
| `stats` | per-second frame and latency statistics |
| `keymap_linux_to_qnum.h` | evdev key codes to QEMU's (generated by keycodemapdb) |

## Local changes

| file | change | why |
|---|---|---|
| `renderer.cpp` | the "swapchain: the compositor scans out / composites the window" line is printed once the scanout vote held 2 s | at the edge of its majority the vote flips with every frame, which filled the app's log |
| `renderer.cpp` | wp_presentation is bound at version 2 when the compositor offers it (was 1) | under a variable refresh rate (VRR) a version 1 client gets refresh 0 in its presentation feedback (KWin: presentationtime.cpp), so QEMU never learns the period and keeps its default; version 2 gets the mode's rate |
| `renderer.{h,cpp}` | `Renderer::setRenderTarget()`: a surface of the caller's own (vitrine's `ViewSurface`) through which the render thread makes its context current, gets its size in buffer pixels, presents the Qt-swap fallback (the first frames, no own swapchain) and lets go at its end; with one set, `setWayland()` changes nothing and the window's own surface is never used | the render thread committed on Qt's surface of the window with nothing in step with Qt (qt-client.md F3): Qt's hide (attach NULL, commit), its re-creation of the surface (re-parenting, destroy) and its configures raced the frames |
| `renderer.cpp` | with a render target, a guest buffer on the surface is taken off it (attach NULL) while the window is not exposed | Qt's hide did that on its own surface; on a surface of the caller's, the compositor would keep the buffer, and QEMU the guest's flushes of it until they time out (8 refreshes each) |
| `renderer.cpp` | the read fences of the guest's buffers are polled without Wayland too (the reader thread runs with no display, the fences alone), woken through an eventfd when one is queued; without a reader thread a copy waits for the GPU (glFinish) and releases at once | the fence fd of each copied frame waited in pendingReads for a reader thread that only exists with Wayland handles: a render thread started without them (X11, or vitrine's window made while the main window was exposed) leaked one sync_file per copied frame (60/s; "Too many open files" on the user's desktop) and never released the buffers. The wake-up also polls a new fence at once rather than at the next Wayland event or after 100 ms (qt-client.md F2, L4) |
| `listener.{h,cpp}` | after closing its connection, the listener thread runs what the close queued on its context | the close queues the connection's "closed" signal on the listener's GLib context, which nothing ran after the loop: its source kept the connection, and the connection the context, an eventfd for every listener stopped while QEMU was connected (each detach) |
| `listener.{h,cpp}` | `stop()` quits the loop through the thread's context (`g_main_context_invoke`) and cancels the handshake (a `GCancellable`) | a quit sent before the thread reached its loop (still in the handshake: a view taken down right after it attached) was lost, and the join waited for ever; a handshake QEMU does not answer blocked it too (qt-client.md F10) |
| `listener.cpp` | a plane without its own fd gets a duplicate of the first plane's with `F_DUPFD_CLOEXEC`, not `dup()` | a plain dup is inherited by the processes vitrine starts later (another VM's QEMU), keeping a guest's dma-buf open in them (qt-client.md L2) |
| `dbusdisplay.{h,cpp}` | one `GCancellable` per display, passed to its asynchronous calls and cancelled in its destructor; the UIInfo.Apply completion returns at once when cancelled, RegisterListener's no longer warns then | GLib completes the calls later, on the GUI thread, with a raw pointer to the display (UIInfo.Apply) or its statistics (input calls): a display deleted with calls in flight was written through then (qt-client.md F14; a test crashed in the uiInfoApplied emission). vitrine's VmView also keeps the display until the completions ran (retire()) |
| `displaywindow.{h,cpp}` | the guest's mouse buttons down are tracked and released on a Leave, when the window loses the keyboard (`setHostActive(false)`), when the grab goes and when the mouse mode switches; relative motion goes to the guest only while the compositor has the pointer locked | Qt forgets a button when the compositor takes the pointer away (its own grab, a screen lock: `wl_pointer.leave` without a release), and the guest kept it pressed, dragging with the next motion; after the compositor unlocked the pointer, relative motion still went to the guest (qt-client.md F11) |
| `displaywindow.cpp` | the pointer lock (grab of a guest with a relative mouse) is taken on the top-level window's surface, as the confinement is, not on the view's own | KWin honours pointer constraints only on a window's main surface: embedded in vitrine's window, the view is a subsurface, and a lock on it never took effect (the pointer left the view). Checked on KWin 6.7.5 (nested): the lock takes effect, relative motion reaches a guest without a tablet, and with the grab Meta + right button reaches the guest while KWin resizes the window without it |
